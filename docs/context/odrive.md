# 台車駆動の測定・検証記録

台車の駆動輪（HB-139 ×2）とモータードライバ（Makerbase ODrive v3.6-56V、
シリアル `0x315536763335`）の立ち上げで行った測定・検証を日付順に記録する。
ODriveはtrail-pcにUSB接続し、`odrive==0.5.4` から操作した。
操作手順は [ODriveツール](../../tools/odrive/README.md)、ROS 2側の制御は
[aha_base](../../overlay_ws/src/aha_base/README.md)（USB）と
`upstream/astra_controller/astra_controller/base_controller.py`（CAN）を参照。

## 2026-11-08 — ファームウェア更新・校正と最初の閉ループ試験

この日の記録は、作業時のメモから再構成した。生ログは残っていない。

### 条件・過程

- ファームウェアをdfu-utilでv0.5.6へ更新した。`odrivetool dfu` は、MKS基板のOTPに
  ハードウェア版数がなく失敗した。更新前の設定は `~/odrive-fw/config_backup_fw0.5.1_20261108_162634.json`（trail-pc）に退避した。
- AhaRobotの設定とCAN（250 kbps、node 0/1、`encoder_rate_ms` 10）、
  ブレーキ抵抗2 Ωを設定して保存した。
- モーター校正は `calibration_current` 5 Aで行った。結果はaxis0がR = 0.570 Ω・L = 0.486 mH、
  axis1がR = 0.495 Ω・L = 0.460 mHだった。
- axis0のホール極性校正は繰り返し失敗したため、axis1の `hall_polarity`（0）を流用した。
  エンコーダオフセット校正の結果は、axis0が `direction` −1・`phase_offset` −65、
  axis1が `direction` 1・`phase_offset` 70だった。
- 右輪（axis1）を浮かせて閉ループ（`pos_gain` 20、`vel_gain` 0.1、電流制御帯域1000）にしたところ、
  激しく振動したため非常停止した。

### 問題・不明点

振動の原因はこの日には特定していない。ゲインやKtをどの値から決めたかは記録がない。

## 2026-11-15 — axis0のオープンループ回転とホール信号の雑音

### 背景・条件

閉ループで振動した原因を探るため、axis0（M0、左）だけをつなぎ、
オープンループ（lockin）とホール信号を調べた。車輪は浮かせた。
電源電圧（vbus）は26.2 V、`encoder.config.bandwidth` は50。
保存済み設定では `encoder.config.ignore_illegal_hall_state` が両軸とも `True` で、
`motor.config.torque_constant` は既定値の0.04 Nm/Aのままだった。
いつ誰がこれらの値を設定したかは記録がない。
試験中は設定を保存していない。

### 観測

- **ホール未接続でのlockin**：5 A・20 rad/s（電気角、機械0.32 rev/s）で5秒回り、エラーはなかった。
  `hall_state` は7で、`ignore_illegal_hall_state` によりエラーにならなかったと考えられる。
- **プルアップ**：fw 0.5.6はホール入力を `GPIO_NOPULL` で初期化する。ホール未接続で入力は3.3 Vで、
  電源を切った状態でテスターの向きを入れ替えて測ると、A端子と3.3 Vの間は3.26 kΩ・3.06 kΩだった。
  基板上に約3.3 kΩのプルアップがあると判断した。他の端子は測っていない。
- **手回し**：ホールは3→2→6→4→5→1の順に変化し、0/7や飛びはなかった。約5回転でshadow_countは+306だった。
  1回転60カウント（極対数10）と矛盾しない。
- **通電中の雑音**：lockin 5 A・20 rad/sでは、短い化けが定速中も続いた。化けは3本すべてに出て、
  2–3本が同時に反転するものが多かった。各ビットのhighの割合は0.50 / 0.51 / 0.50で、
  ロータの追従（shadow_countの増え方と指令の比）は1だった。無通電では化けは0件だった。
- **モーター校正の再測定**：axis0で3回測り、R = 0.387 / 0.387 / 0.388 Ω、L = 0.462–0.463 mHだった。
  11月8日の0.570 Ωとの差は仮配線の接触抵抗と考えられる。この値は保存しておらず、その後の再起動で消えた。
- **PLL帯域**：lockin 5 A・20 rad/s（真の速度0.318 turn/s）で `vel_estimate` の標準偏差を測った。
  bandwidth 20で6%、50で61%、100で156%、200で170%だった。50では平均も+10%ずれた。

### 条件別の記録

`tools/odrive/hall_record.py --plan baseline` で記録した。
記録は `~/odrive-fw/logs/hall_20261115/`（trail-pc）にある。
ホスト側の読み取りは2.7–4.6 kHz。値は `hall_analyze.py` による定速区間の集計。

| 条件 | ノイズ/秒 | 0/7/秒 | 追従 |
| --- | --- | --- | --- |
| 無通電（開始・終了） | 0 | 0 | — |
| 5 A・20 rad/s | 21.7 | 14.2 | 1.10 |
| 5 A・40 rad/s | 26.4 | 18.1 | 1.00 |
| 5 A・80 rad/s | 18.1 | 10.3 | 1.02 |
| 5 A・120 rad/s | 17.3 | 9.5 | 1.00 |
| 2 A・20 rad/s | 31.6 | 20.1 | 1.07 |
| 3 A・20 rad/s | 25.5 | 18.4 | 1.07 |
| 8 A・20 rad/s | 9.8 | 5.8 | 1.17 |

- 1秒あたりのノイズは速度によらず17–28件で、電流を上げると減った。
- ノイズの多い状態は、20–40 rad/sでは1・2、80–120 rad/sでは3・5に移った。
- 2 rad/sの角度スイープはコギングで進退を繰り返し、追従が4.97となり、雑音を分離できなかった。
- 逆転の2条件は、スクリプトがlockinの `accel` を負にしたため無効。磁界が正方向へ加速し続け、
  車輪は正転方向へ約2.1 rev/s・3.1 rev/sで回った。エラーはなく、FETは最高34℃だった。

### ファームウェアの読み取りとフィルタの評価

fw-v0.5.6のソースで次を確認した。

- ホールは制御周期（8 kHz）ごとに、電流測定と同じタイミングで1回読む。
- 転流の角度は、PLLを通さない生のカウントに補間を足して計算する。PLLの帯域は転流に効かない。
- カウントの増分は、状態番号の差を6で割った余りを−2〜+3に変換して求める。3ビット反転の化けは、
  行きも帰りも+3となり、1回で+6カウント（車輪1/10回転）ずれる。

記録へフィルタ候補を当てた結果（`hall_filter_eval.py`）、5 A・20 rad/sでは次のとおりだった。
標準の処理ではカウントが+12ずれ、速度推定の平均は+7.4%、ばらつきは54.9%だった。
隣接遷移だけを受け付けると、ずれは0になったが、隣接への化けが21件/秒残った。
隣接遷移が0.25 ms続いたときに受け付けると、偽の遷移は0.4件/秒になった。
遅れは中央値0.37 ms、速度推定のばらつきは参照系列と同じ21.5%だった。

ファームウェアへ実装した同じ処理を、記録を8 kHzへ揃えた入力で動かした結果は次のとおり。
`hall_debounce_cycles` 4（0.5 ms）で、偽の遷移は全条件で0.2–6.8件/秒、カウントのずれは0、
遅れは0.38 msだった。ホストの読み取りは1標本を2–3周期へ引き伸ばすため、
実機での短い化けへの効き方は、この評価より良い可能性がある。

### 決定と根拠

- ハードウェアの対策（ホール入力のコンデンサ）は行わず、ファームウェアのフィルタで進める。
- 閉ループへ戻る前に、エンコーダオフセット校正をやり直す。試験中にホール線をつなぎ直したため。
  相線は変えていない。つなぎ直し後はlockinの正方向でshadow_countが増え、つなぎ直し前は減った。
  2本の入れ替えと矛盾しない。

### 確認範囲・不明点

- 実機で確認したのはaxis0だけ。axis1は未接続で測っていない。
- 逆転方向の雑音は有効な記録がない。
- 化けの実際の幅は、ホストの読み取り間隔より短く、わからない。ロジックアナライザでは確認していない。
- ホールをつなぎ直した後の配線（色と端子の対応）は記録していない。
- フィルタ付きファームウェアは実機へ書き込んでいない。

### Ktの測定

速度制御（`vel_gain` 0.02、`vel_integrator_gain` 0.1）で±0.5・1.0・1.5 turn/sを各6秒回し、
後半3秒の平均から逆起電力を求めた。電流制御の出力電圧は、fw 0.5.6では `Vq_setpoint` が0のままのため、
`current_control.v_current_control_integral_q` を使った（`final_v_alpha/beta` の大きさとも1%以内で一致）。

- (Vq − R·Iq) ÷ `phase_vel` は6点とも0.0249–0.0251 Vs/rad（電気角）で、直線の切片は+0.002 V。
- Kt = 1.5 × 極対数10 × 0.0249 = 0.374 Nm/A（8.27/Kt = 22.1）。既定値0.04の約9.3倍。
- 無負荷の一定速度でIqは0.12–0.15 Aだった。

速度上限は安全のため1.5 turn/s）とし、`current_lim` 5 Aと同じ監視を付けた。

- 左 `sign` −1・右1で、前進・後退・左旋回の向きはodomと一致した。
- 定常区間（各段階の1.5秒以降）の平均は、前進0.148 m/s、後退−0.147 m/s、旋回0.572 rad/sだった。
- `vel_estimate` から求めたodomの速度は揺れが大きく、前進中の角速度の標準偏差は0.25 rad/s、
  旋回中は0.36 rad/sだった。位置の差から求めても、0.3秒の窓で0.13–0.29 rad/s、0.5秒の窓で0.04–0.16 rad/sだった。
  浮かせた状態で車輪の回転そのものがむらになっていると考えられる（前日の低速のスティックスリップと同じ現象か）が、確かめていない。
- 保持中に送信を止めると、0.48秒後に両軸がIDLEになり、`axis.error` は0x800（`WATCHDOG_TIMER_EXPIRED`）だった。
  `axis.config.enable_watchdog` / `watchdog_timeout` / `watchdog_feed()` がファームウェア0.5.6で働くことを確かめた。
- 停止後、両軸はIDLEで、RAMで変えた値（`input_mode`、台形軌道、`current_lim`、watchdog、axis1のKt）は元に戻った。
