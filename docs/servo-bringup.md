# サーボ立ち上げ実測メモ (2026-09-06)

実機のアーム 1 本を対象に、配線・可動域・対向取付の符号を実測した記録。
測定に使ったスクリプトは [`tools/servo/`](../tools/servo/README.md)。

## 結論 (先に)

1. 実機のサーボは **12 個** (`ID 4-15`)。当初 ID14 が未実装だったが後から追加され、
   現在は upstream が期待する構成と一致している
2. 対向取付の符号が upstream のリファレンスと違う。両関節とも `{+1,-1,-1,+1}`
   (upstream は全関節 `{+1,-1,+1,-1}` を決め打ち)
3. 制御基板には AhaRobot のファームがまだ載っておらず、Waveshare 純正デモのまま

2 は、そのまま `AstraArmController` を焼くと**壊れる**。
[`patches/AstraArmController-trail-club-hardware.patch`](../patches/) を当ててから焼くこと。

## 制御基板

| 項目 | 値 |
| --- | --- |
| 基板 | Waveshare "Servo Driver with ESP32" (ESP32-D0WD-V3 / 4MB / SSD1306 OLED) |
| MAC | `28:05:A5:C4:F7:44` |
| 載っているファーム | Waveshare 純正デモ (AhaRobot のものではない) |
| AP | SSID `ESP32_DEV` / PW `12345678` → `http://192.168.4.1/` |

純正ファームは USB シリアルを透過しない。ESP32 がバスのマスターなので、
素の状態で STS プロトコルを流しても**一切応答がない**。Web UI の
**Start Serial Forwarding** で透過ブリッジになり、`/dev/ttyUSB0` を 115200bps で
開けば直接叩ける。手順は [`tools/servo/README.md`](../tools/servo/README.md)。

純正ファームのダンプ (app0 / nvs / partition table) は焼く前に取得済み。

### 純正ファームの HTTP API

`GET /cmd?inputT=T&inputI=I&inputA=0&inputB=0` / `GET /readID` / `GET /readSTS`

| T | I | 動作 | T | I | 動作 |
| --- | --- | --- | --- | --- | --- |
| 9 | 0 | サーボ検索 | 1 | 7,8 | Speed +/- |
| 0 | ±1 | アクティブID 選択 | 1 | 9,10 | ID to Set +/- |
| 1 | 1 | 中点へ移動 | 1 | 11 | 中点校正 (EPROM 書込) |
| 1 | 2 | 停止 | 1 | 12,13 | サーボ/モータモード |
| 1 | 3,4 | Release / Torque | 1 | 14,15 | **シリアル転送 開始/停止** |
| 1 | 5,6 | Position +/- (押下中) | 1 | 16 | ID 書き換え (EPROM 書込) |

## サーボ構成

STS3215 (model 777)。電源 12.1-12.2V、温度 33-37℃ で全個体正常。

| 系統 | ID | 構成 |
| --- | --- | --- |
| joint0 | 4, 5, 6, 7 | 4 個で 1 関節を対向駆動 |
| joint1 | 8, 9, 10, 11 | 4 個で 1 関節を対向駆動 |
| 単発関節 | 12, 13, 14, 15 | 15 がグリッパ |

### ID14 は後から追加された

当初 ID14 のサーボが実装されておらず、ID 0-252 の全域スキャンでも不在だった。
その後実機に追加され、現在は 12 個すべてが応答する。

upstream は単発関節の ID を `12,13,14,15` の連番で決め打ちしているが、機体に
よっては欠けることがあるので表 (`NONE_JOINT_ID`) にした。`-1` を入れるとその
スロットは読み書きを飛ばし、常に 2048 (= 0 rad) を返す。自由度を減らさず
スロット数を 6 のまま保つのは、`NONE_JOINT_NUM` を減らすと

- 通信パケットが 6 個の uint16 固定 (`comm_payload_size` 16 バイト、`main.cpp` も `i < 6`)
- `arm_controller.py` の `to_si_unit` が `arr[-1]` をグリッパとして扱う
- `JOINT_MIN` / `JOINT_MAX` も 6 要素

と連鎖的に壊れるため。現在の実機では欠番がないので `{12, 13, 14, 15}` を入れている。

## エンコーダ原点と中点校正

STS3215 の位置は 0-4095 の絶対値で、原点 (0/4095 の境目) をまたぐと読み値が
0 と 4095 の間で飛ぶ。位置指令も範囲外を出せず、負の値を送ると 0xFF.. が送出されて
サーボが桁違いの位置と解釈し**逆回りに全力で回る**。

実機は当初 11 個中 6 個 (ID6, 7, 9, 10, 13 と ID5) が原点から 150 step 以内に
止まっており、joint0 / joint1 が片側にまったく動かせなかった。
`tools/servo/rezero.py --apply` で全数の中点を取り直して解消した。

可動域を測ったあと、`rezero.py --center <calibration.json>` で実測中心が 2048 に
来るようオフセットをずらす。オフセットを +1 すると読み値が -1 されるので
`新オフセット = 旧オフセット + (実測中心 - 2048)`。オフセットは符号ビット (2048) と
大きさ 11bit の形式で、範囲は [-2048, 2047]。

## 対向取付の符号 (最重要)

トルクOFFで手動で動かし、軌跡の相関から求めた。いずれも `|r| = 1.00`。

**joint0** (台座固定後に測定)

|  | ID4 | ID5 | ID6 | ID7 |
| --- | --- | --- | --- | --- |
| ID4 | -- | -1.00 | -1.00 | +1.00 |
| ID5 | -1.00 | -- | +0.99 | -1.00 |
| ID6 | -1.00 | +0.99 | -- | -1.00 |
| ID7 | +1.00 | -1.00 | -1.00 | -- |

**joint1**

|  | ID8 | ID9 | ID10 | ID11 |
| --- | --- | --- | --- | --- |
| ID8 | -- | -1.00 | -1.00 | +1.00 |
| ID9 | -1.00 | -- | +1.00 | -1.00 |
| ID10 | -1.00 | +1.00 | -- | -1.00 |
| ID11 | +1.00 | -1.00 | -1.00 | -- |

```c
const int JOINT_SERVO_SIGN[4 * JOINT_NUM] = {
  +1, -1, -1, +1,   // joint0: ID4, ID5, ID6, ID7
  +1, -1, -1, +1,   // joint1: ID8, ID9, ID10, ID11
};
```

upstream の決め打ち `{+1,-1,+1,-1}` に対して **3 番目と 4 番目が逆**。
両関節が独立に同じパターンを示したので、測定誤差ではなく組み付け規約の系統差。

**符号が違ったままトルクを入れると、4 個のうち 2 個が残り 2 個を PWM 800/1000 で
押し返して関節が固着するか機構を壊す。**

サーボの ID 振り直しではなく、ファーム側を実機に合わせる方針にした
(ID 振り直しは EEPROM 書込が必要で、ファームはまだ焼いていないため)。

### 台座固定が測定の前提

根元を台座に固定していないと、joint0 の `{4,5}` と `{6,7}` は互いに
**無相関 (r ≈ 0.01)** になり符号が測れない。固定するか、根元を手で
押さえた状態で測ること。`teach_calibrate.py --verify` はこの状態を検出して
「★未確定」と警告する。

## 可動域

中点校正後に `teach_calibrate.py` で手動計測した値 (ID14 追加後、551 サンプル)。
生データは [`tools/servo/data/rom-2026-09-06-12servo.json`](../tools/servo/data/)。

| 関節 | ID | 可動幅 (step) | 角度 | teleop の可動量 |
| --- | --- | --- | --- | --- |
| joint0 | 4-7 | 1607-1623 | 141-143° | ±920 |
| joint1 | 8-11 | 1874-1901 | 165-167° | ±990 |
| wrist12 | 12 | 4724 | **415.2°** | ±1950 (頭打ち) |
| wrist13 | 13 | 2874 | 252.6° | ±1360 |
| wrist14 | 14 | 3504 | 308.0° | ±1650 |
| gripper | 15 | 2775 | 243.9° | ±1310 |

joint0 / joint1 はこの回より、中点校正前の計測 (611 サンプル、
[`rom-2026-09-06-11servo.json`](../tools/servo/data/)、joint0 span 2001-2076 /
joint1 span 2105-2114) のほうが端まで振れている。teleop の可動量 (±920 / ±990) は
そちらの半分から余裕を引いた値。手動計測なので毎回端まで振れるとは限らず、
可動幅は「少なくともこれだけはある」下限として読むこと。

グリッパは `GRIPPER_GEAR_R = 0.027/2` より 1 step ≈ 0.0207mm。可動幅 2775 step は
ジョー移動量 約 57mm。

### ID12 は 1 回転に収まらない

可動域が 415° あり、1 回転 (4096 step) を超える。位置指令は中点から片側 2047 step
までしか出せないので、**両端の約 30° ずつは位置モードでは指令できない**。
`keyboard_teleop.py` の `MAX_ROM = 1950` で頭打ちにして、範囲外の指令が出ないように
している。全域を使いたい場合は機構側にストッパを設けるか、多回転を扱える制御に
変える必要がある。

### 中心合わせの実施状況

`rezero.py --center` でオフセットをずらし、実測中心が 2048 に来るようにした。

| ID | 実施内容 |
| --- | --- |
| 4-11 | ずれが 38 step 以下だったので変更なし |
| 12 | -608 |
| 13 | +358 |

## 焼く前に把握しておくこと

`arm_controller.py` の `do_init=True` が呼ぶ `setupTorque(128)` は、

- **ID4-11 の動作モードを PWM モードに書き換える (EEPROM 書込)**
- グリッパ ID15 の中点を offset 1448 で強制的に書き換える
- バックラッシュ中点 `config.init_pos[]` を測定して ESP32 の EEPROM に保存

一度実行すると純正ファームに戻しても設定は残る。
